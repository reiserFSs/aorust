
## installer

Ported from the decompiled PRK launcher (`MainWindow.DownloadLatestVersion`, `HttpPatchServerService`, `VersionMap`, `VersionIdentifier`, `DeletionHandler`, `RDBController.ApplyRDBPatch`). Implementation: `crates/ao-install`.

- **Map**: `GET https://patches.project-rk.com/patches/patches.map`, lines `src = dst` (split on `=`; lines not giving exactly 2 parts are ignored). Many sources map to `0.3.0`/`0.5.0`; the main chain is `0.0.0=0.6.1`, `0.6.1=0.6.2` … `0.6.36=0.7.0`, `0.7.0=0.7.1`, `0.7.1=0.7.2`.
- **Version** (`VersionIdentifier`): `M.m.p[-pre][+build]`, equality is field-wise (pre-release parts after the first `-` are concatenated). Current version = `patch.version` in the client root, else `0.0.0`.
- **Loop**: while a patch with `src == current` exists: download `patches/<dst>.zip` → extract over the client dir with overwrite → if `<dst>.rdbpatch` in client root: apply and delete it → delete zip → if `<dst>.df` in client root: process it (file stays) → write `patch.version = dst` (tmp file + rename). Any failure before that leaves `patch.version` untouched: extraction overwrites and the rdbpatch is one `INSERT OR REPLACE` transaction, so a rerun redoes the step; an unreadable zip is deleted so it is re-downloaded. Unit test `failed_patch_keeps_version` injects a corrupt zip, a zip-slip entry and a truncated rdbpatch.
- **Zip**: paths relative to client root (e.g. `cd_image/...`); we reject entries that escape it (zip-slip). Resume: partial zip is kept in `<client>/../downloads/<dst>.zip`, continued with HTTP `Range`. Verified live: `0.7.0.zip` (140 733 024 B) killed at 25 173 681 B, rerun sent `Range: bytes=25173681-` → server `206`; result sha256 `22a5f7e7…edf1de` equals a fresh `curl` download (server sends `Accept-Ranges: bytes`, `ETag`). A 416 is only trusted if a HEAD `Content-Length` equals the local size (else the stale file is deleted and refetched); a 206 is only appended if `Content-Range` starts at the local size (else restart from 0). `apply_rdbpatch` opens `rdb.db` without CREATE (missing db = error); `patch.version` temp file and the client dir are fsynced around the rename. Covered by unit tests with a local HTTP server.
- **`.rdbpatch`**: `i32 count`, then per record `u32 type, u32 instance, u32 version, i32 len, bytes[len]` (little endian). The launcher ignores the per-record version and runs `INSERT OR REPLACE INTO [rdb_<type>] (id, version, data) VALUES (<instance>, 1, <bytes>)` on `cd_image/rdb.db`. We do it in one transaction (missing tables are created with the same schema).
- **`.df`**: one client-relative path per line; existing files are deleted, then emptied parent directories (never the client root) are removed. We reject absolute / `..` entries. Backslashes are treated as separators (the shipped `0.6.3.df` is `cd_image\twk\Tweak_….txt`; the launcher only maps `/`, so on non-Windows it would never match). Of all 50 zips in patches.map (central directories read by ranged GET) only `0.6.3.zip` contains a `.df`; `.rdbpatch` is in 0.5.1–0.5.3 and 0.6.2–0.6.36. Scratch run `0.6.2→0.7.2` in `/tmp/aoi-scratch`: the listed file was deleted, sibling kept, `0.6.3.df` left in place and every `.rdbpatch` removed — identical to the launcher (`RDBController.ApplyRDBPatch(deleteWhenDone=true)` deletes the rdbpatch; `MainWindow` never deletes the `.df`).

## renderer

`ao-render` consumes `ao_scene::Scene` only (no format knowledge). wgpu 24 / Metal, winit 0.30.

- GPU layout: per mesh one vertex buffer (48 B: pos, normal, uv, linear RGBA colour) + one u32 index buffer; instances (mat4, step mode Instance) live in a 3-buffer ring rewritten every frame with the frustum-visible instances, grouped by mesh, so one `draw_indexed` per submesh covers all visible instances of that mesh. Per (texture, `base_color`) one bind group (texture, sampler, 16 B uniform). Textures: RGBA8 sRGB, CPU box-filter mip chain, **Repeat** addressing, linear mip filter, 16x anisotropy (one shared sampler, so terrain textures included); submeshes without a texture (or with an invalid one) use 1x1 white. 4x MSAA, Depth32Float.
- Pipelines: 4 blend modes x {culled, two-sided} = 8. Front = CCW, back faces culled unless `two_sided`. Opaque / AlphaTest (`discard` at alpha < 0.5, depth write) draw first, sorted by pipeline/mesh/material. AlphaBlend (src-alpha, no depth write, constant -2 / slope -2 depth bias so coplanar overlays win against the opaque base) and Additive (src-alpha x dst-one, glow fades out with fog rather than tinting) draw afterwards as one draw per (visible instance, submesh), sorted far-to-near by instance bounding-sphere centre; ties (submeshes of one instance) keep submesh order. Fragment = texel x vertex colour x `base_color`; lit = ambient + sun_colour * max(N.L, 0) with the normal flipped toward the eye; fog is linear (`fog_start`..`fog_end`) toward `fog_color`. Clear colour = `Environment::sky_color`; far plane = 1.1 x `fog_end`. `Environment` None -> defaults (sky sRGB 0.53/0.72/0.92, fog start/end = 0.5/1.0 x max(2 x scene radius, 300 m), ambient 0.35/0.38/0.45, sun 0.75/0.71/0.64 from (0.4, 0.8, 0.3)).
- **Self-illumination** (shader.wgsl): material uniform = `base_color` + `emissive` + glow flag (32 B; bind group key includes them). `lit = tex * vertex * base_color * (light + emissive)` (engine: `tex * (emissive + lighting)`, RE in § meshes) with `light = ambient + sun + point lights`; for `glow_mask` submeshes `light = max(light, min(light + tex.a, 1))` per channel (engine `saturate(a + lighting)`, never darker than the plain lighting). Emissive is applied before fog; no tone mapping/clamp of the sum.
- **Point lights** (`Scene::lights`, static): `LightGrid` built once in `upload`: dense 3D grid over the lights' AABB (+ range), cell edge 8 m, doubled until <= 2^20 cells; each light is written into every cell its sphere touches (sphere/box test); per cell the `CELL_LIGHTS = 16` best are kept, ranked by `(r+g+b) / (|cell centre - light|^2 + cell^2)`; dropped lights are simply absent in that cell (hard cap, no popping inside a cell, minor discontinuity at cell borders). GPU: three read-only storage buffers (lights as `vec4` pairs, cells `(first, count)`, index list) next to the globals uniform; the fragment shader looks up the cell of its world position and loops <= 16 lights: `colour * (1 - d/range) * wrap`, `wrap = clamp((N.L + 0.5) / 1.5, 0, 1)` (half-lambert-ish; calibration guess, no engine formula known), N flipped toward the eye as for the sun. Applies to every lit submesh (meshes, terrain, dungeon shells, characters). Cost is per fragment, independent of the light count: 11 000 random lights (6-26 m range) packed into 160x160 m around the spawn: pf 505 2.0 ms (0 lights 2.0), pf 566 2.1 ms (0 lights 1.9) at 1280x800 logical, NOVSYNC. Sky/additive/blended submeshes use the same shader, so blends are lit too.
- **Sky** (`Scene::sky`, `Instance`s of `meshes`, not in `instances`): drawn first in the same pass with dedicated pipelines (`vs_sky`/`fs_sky_*`, indices 8..12): no culling, no depth write, depth compare Always, clip z pinned to the far plane (a dome larger than the view distance is not clipped), no lighting/fog (`rgb * (1 + emissive)`), blend modes honoured. The instance transform keeps rotation/scale but its translation is replaced by the camera position every frame (instance buffer ring `sky_bufs`). Demo: dark gradient sky box, emissive cube, glow-mask window cube and four coloured lights at dusk (`aomac view demo`).
- Culling: per-mesh bounding sphere (AABB centre, max vertex distance) scaled by the largest transform axis length, tested against the 6 view-frustum planes on the CPU each frame.
- wgpu 29 (not 24): `block v0.1.6` (future-incompat warning) is pulled in by `metal` 0.31-0.33, i.e. by wgpu-hal 24-28; wgpu-hal 29 uses objc2-metal and the warning is gone.
- Camera: `Scene::spawn` (looking at `spawn_look_at`, else horizontally toward the bounds centre) if set, else a 3/4 view framing the instance bounds. `--eye/--at` override it for both the screenshot and the interactive viewer.
- Viewer controls: WASD move, Space/E up, Ctrl/Q down, Shift ×5 speed, scroll = speed ×1.15 per notch, hold right mouse = mouse-look (cursor locked), Esc quits. Title shows FPS, position, speed. `AOMAC_NOVSYNC=1` disables vsync, `AOMAC_PERF=1` prints start camera, scene bounds and per 0.5 s ms/frame, `render()` CPU ms, visible instances and draw calls to stderr.
- Headless: `ao_render::render_to_png(scene, eye, look_at, w, h, path)`.
- CLI (`--client DIR` default `~/Games/ProjectRubiKa/client`):
  - `aomac install [--client DIR]` → `ao_install::run`
  - `aomac view mesh <id>` / `view char <id> [--anim A --time S]` / `view pf <id>` / `view pf --list` / `view demo [--count N]`
  - on any view: `--screenshot out.png [--eye x,y,z] [--at x,y,z] [--size WxH]` renders offscreen and exits (defaults: `ao_render::default_view`, 1280x800).
- Perf (M4 Pro, release, 1280x800 logical = 2560x1600 px window, 4x MSAA, `AOMAC_NOVSYNC=1`, ms/frame; before = old renderer that drew every instance, no culling, treated all non-opaque blends as cutouts): pf 505 spawn view 2.95 -> 2.1-2.5; pf 566 spawn view 1.8 -> 0.85 (wgpu 29) ; pf 505 from 2.5 km up with ~26.6k statels visible 2.3 -> 5.3 (6689 draws; 5.7k of them are per-instance sorted AlphaBlend submeshes, CPU 2.7 ms; with those batched as opaque it is 4.2, so true sorted blending costs ~1 ms per 5.7k instances: producers should prefer AlphaTest for foliage cutouts); pf 566 from 500 m up 1.7 -> 1.9. Spawn-view numbers include scene changes by other slices between measurements. Demo `--count 10000`: 1.5-2.2 ms.

## meshes

Implementation: `crates/ao-formats/src/{archive.rs,mesh.rs}`; survey tool `cargo run --release -p ao-formats --example mesh_stats`.
Ground truth: Ghidra 12.1.4 decompilation of `randy31.dll` (the "Randy" engine; PE image base 0x10000000, addresses below are VAs): `RRefFrame_t::Archive` @10044da8, `RRefFrame_t::RRefFrame_t(ObjectArchive_c*)` @10045a2f, `RRefFrame_t::UpdateWorldMatrix` @10044fa2, `RVisualData_t::Archive` @1004ea04 (the `FAFTriMeshData_t` base), vertex-buffer (de)serialisers @1004883e / @10048a5c, `RDeltaState::Archive` @1002f145. No community documentation of this format was found; everything here comes from the DLL plus the data.

### Record types
- `rdb_1010001` (9925 records, 352 MB): "static meshes" — scenery, buildings, props, trees, doors, lamps, *and* animated/effect meshes. Ids 1414…289317. A record is a whole node tree (one model), not a single triangle soup.
- `rdb_1010026` (699 records, 14.6 MB): same container and classes, **every id also exists in 1010001**, ~3× fewer triangles (e.g. 1495: 176 → 12 tris, 134 → 18 verts), single node, keeps the same textures: a **reduced-detail mesh**. Code evidence (type ids 1010001 = 0xf6951, 1010026 = 0xf696a): `n3VisualDynel_t::HasMesh` (N3.dll @10019514) accepts both as "plain mesh" (the CAT pair 1010002/1010027 = 0xf6952/0xf696b is `HasCatMesh` @100194f9); `RDBMesh_t::ReduceMesh` (DisplaySystem.dll @10077095) derives a 0xf696a `DbObject` with the same id from a 0xf6951 one by keeping only the four `SimpleMesh`es with the most vertices (returns null when the source has < 4) and cloning the rest of the node; the one consumer found is `AOPlayfieldCityHolderClient_c::EnableVisibility` (Gamecode.dll @1012e58b), which builds `VisualMesh_t`s from `Identity{0xf696a, id}` for the `HouseVisualData` list of a player-city holder and registers them with `LODManager::AddMesh` (distant city houses). So it is a LOD proxy used by the city/LOD path; statels and ordinary visuals reference 1010001. `[INFERENCE: the shipped records do not all have ≤ 4 submeshes (num_meshes 1…21), so they were generated by a different/earlier tool than ReduceMesh; the distance switch inside LODManager is in a DLL that was not decompiled]`. `mesh::decode_record_into(.., MESH_LOW_TYPE, ..)` decodes it; `decode_mesh_into`/`load_mesh` use 1010001.
- Textures referenced by meshes: `rdb_1010004` (32 629 refs: JPEG or PNG-with-alpha) and `rdb_1010011` (5 refs); decoded by `texture::load_texture`.
- `1010002`/`1010003`/`1010027` are character models/animations, see § characters. `1010013` (363 small records beginning `02 00 00 00`, floats follow) and `1010025` (one record of animal names "Beetle/Bird/Bunny") are not meshes of this format.

### Container: Funcom `ObjectArchive` (little endian)
```
u32 version = 3
u32 range_count
range_count x { u32 value; char name[32] }   named animation ranges ("idle","walk","shotgun_reload"…), 0xCD padded; 36 bytes each
u32 w0, u32 w1(=1)                           not used by the reader (w0 is 0 or a small packed value such as 0x07000700)
u32 name_count (<=256)
name_count x { cstr kind; cstr name }        kind = "" starts a class (name = class), else a member "digit"; names are indexed globally 0..name_count
u32 object_count
(object_count + 1) x object                  object 0 is a holder with a single member "obj" (ref) = index of the root object
object := u32 type_id, u32 version(=1), u32 member_count, member_count x member
member := u8 name_index, u32 type, u32 elem_size, u32 total_size, bytes[total_size]
trailing: 12+ zero bytes
```
Evidence: record 1010001/287726 (311 B, an empty `RRefFrame_t`): table of 9 names (`RRefFrame_t`, `__class_id__`, `grp_mask`, `local_pos`, `local_rot`, `scale`, `conn`, `chld_cnt`, `obj`), holder member `obj`=0, object 0 has 7 members, file ends exactly 12 bytes after the last member. Records with `range_count` > 0: 7798 (3 ranges), 36077 (idle, walk), 75392 …; before handling the ranges 16 records failed (grouped as "implausible name table"/"no root"), after: all parse.

Member `type` codes seen (self-describing; matches `fun::Message_c::Add*` in the DLL): `0` bool/u8, `3` int32 (arrays when size > 4), `6` string (`u32 len` + bytes, no NUL), `9` raw blob (`u32 len`-prefixed for `vertices`/`triangles`, bare 16 bytes for `vb_desc`), `0xa` f32, `0xc` Vector3, `0xd` Quaternion (x,y,z,w), `0xf` 4x4 matrix (16 f32), `0x10` RGB f32 colour, `0x11` object reference(s) (i32 each; `-1` = null; one member holds all refs of an array, e.g. `mesh`, `chld`, `tch_text`). Repeated scalar members (`rst_type`, `rst_value`, `tch_type`, `tch_text`) appear once per element and must be read in order. `__class_id__` is a per-file running number, not a class tag; objects are classified by their member names. The 1-byte `name_index` limits a record to 256 names.

`vb_desc` = `{u32 16, u32 0x10000, u32 FVF, u32 vertex_count}`; FVF is **0x112** (D3DFVF_XYZ | NORMAL | TEX1) in all 50 159 SimpleMeshes → 32-byte vertices `pos[3] normal[3] uv[2]` (f32). `vertices` = `u32 byte_len` + `vertex_count * 32` bytes. The loader also understands diffuse/specular/extra UV sets generally from the FVF bits.

Render states observed (`rst_type`/`rst_value`; the engine is **D3D7**: `_D3DMATERIAL7`, `_D3DRENDERSTATETYPE`, ids below are D3D7's) over all of 1010001: 15 ALPHATESTENABLE=1 (1363 deltas), 27 ALPHABLENDENABLE=1 (1639) / =0 (1591), 22 CULLMODE=1 (D3DCULL_NONE, 1708), 29 SPECULARENABLE=1 (8395), 145 DIFFUSEMATERIALSOURCE=0 (519). **Never present: 19/20 SRC/DESTBLEND, 24/25 ALPHAREF/FUNC, 14 ZWRITEENABLE, any CULLMODE other than 1.** (145–148 are D3D7's `DIFFUSE/SPECULAR/AMBIENT/EMISSIVE_MATERIALSOURCE`; 0 = take it from the material instead of the vertex colour; `FUN_1004ac5f` @1004ac5f sets 145..147=0 and 148 = (emissive ≤ threshold) on every material, `RenderWithTransparency` sets 146/148=1 when a per-instance colour is bound.) Foliage keeps its states on the **node's** `delta_state` ("alpha", node 11 of 1010001/6273 → `rst 15=1`) while the texture is on the material's `delta_state`; the loader merges both, **material wins** per state id. `tch_type` is the channel (0 = diffuse). Texture-stage deltas only occur as `tst (1, 7)` (COLOROP=ADD, 1011×) and `tst (2, 34)` (COLORARG1=TEXTURE|ALPHAREPLICATE, 1953×).

**Where the states come from (`FUN_10040645` @10040645 = RMaterial transparency preset, mode chosen from a `[n]` prefix of the material name or automatically from the texture's alpha channel, `FUN_1004761a`):** mode 0 texture alpha = transparency (`0x74`/`0xbd` flags, 27=1); 1 alpha test (27=0, 15=1, ALPHAFUNC=GREATER, ALPHAREF=0x80); 2 alpha test ref 0x1e **and** blend (27=1,15=1), z-write off; 3 blend only, z-write off; 4 additive (27=1, SRC=ONE, DEST=ONE, TSS colour op = SELECTARG1(texture)), z-write off; 5 (automatic for textures with alpha when ≥ 2 texture stages and no transparency flag): stage 0 = `texture.alpha(replicated) + diffuse` (COLOROP ADD), stage 1 = `texture.rgb × stage0` (COLOROP MODULATE) with the same texture bound twice, 27=0 — i.e. **the texture alpha channel is a self-illumination mask** (this is the `(27,0)` + `tst (1,7)` pair in the data, ≈1000 materials). `RMaterial_t::IsTwoSided` @10040aff = rst 22 == 1 (NONE); `RMaterial_t::SetOpacity` @10040f61 sets the "transparent" flag `0xbd` (render list 6, back-to-front sort) when `opac` < threshold or the texture has alpha, but if a delta state exists it is overwritten by rst 27==1. `RTriMesh_t::Render` @10049761 puts the mesh in render list 6 when any material is transparent or frame transparency < 1, else list 3 (the `prio` member of the node is 3/5/6: opaque / ? / transparent, i.e. the same sort-list choice; the renderer sorts blended draws itself, `prio` is not exported). Randy never sets SRC/DESTBLEND for mesh materials (only for the sprite/glow classes: `RSprite::EnableAdditiveRendering` @10013128, DisplaySystem @859: SRC=SRCALPHA(5), DEST=ONE(2), z-write off), so plain blend uses the D3D default pair `[INFERENCE: SRCALPHA/INVSRCALPHA, the only pair that makes 27=1 visible]`. Randy never changes CULLMODE globally, so the device default (D3DCULL_CCW; front = clockwise in D3D's left-handed space) applies to every material without `rst 22=1`.

### Transform rule (from `UpdateWorldMatrix` @10044fa2)
Row-vector D3D convention (`v' = v · M`, translation in row 3): `local = R(local_rot)ᵀ · scale, translation = local_pos`; if `anim_matrix` exists: `local = anim_matrix · local`; `world = local · parent_world`. Quaternion → matrix is the standard one, transposed (decompiled @1006e393). `anim_matrix` of mesh nodes equals the object's 3ds-Max node transform (= `FAFTriMeshData_t.anim_pos/anim_rot`, e.g. `Rx(+90°)` for Max Z-up → Y-up: 1010001/214381, `anim_pos` (-0.539, 0.452, -0.454) = `anim_matrix` row 3) and is what makes the vertices upright; `anim_pos/anim_rot` themselves are **not** applied again. Vertices are stored in the mesh node's object space.

### Coordinate conversion (loader output)
Source space is **left-handed, Y up, 1 unit = 1 m** (D3D9; triangles are clockwise-front: for record 214381 the numeric cross product of tri (0,1,2) equals the stored vertex normal −Z). The loader bakes the node tree into one `Mesh`, then **negates Z** of positions and normals (→ right-handed, +Y up) and **reverses triangle winding** (flipped back when a node matrix has negative determinant). UVs are untouched (D3D origin top-left == `Texture` row order). Verified: over all 7.4 M triangles of 1010001 the CCW geometric normal agrees with the vertex normals for 97.7 % (7 217 373 vs 172 241, the rest are flat/double-sided strips); barrel texture 6153 (1010004) renders un-mirrored. **Anything positioned in AO world space (statel placements!) must undergo the same Z negation** (`p' = (x, y, -z)`, rotations conjugated accordingly) to line up with the converted meshes.

Submeshes are merged per `(texture, blend, two_sided, base_color)` (the loader's `MatKey`). Mapping onto `ao-scene::Submesh`:
- `blend`: rst 15=1 → `AlphaTest` (also when 27=1, see mode 2: the cutout survives without depth sorting); else rst 27=1 → `Additive` if DESTBLEND=ONE and SRCBLEND ∈ {ONE, SRCALPHA}, else `AlphaBlend`; else `Opaque`. Untextured submeshes can be blended/tested too (alpha = `opac`).
- `two_sided` = rst 22 == NONE; **default is culled** (back faces of the CCW-front scene-space triangles).
- `base_color` = (`diff` rgb converted sRGB→linear, `opac`). D3D multiplies gamma-space values with a non-sRGB texture; the renderer samples sRGB textures to linear and encodes at the end, so converting the colour with the same power curve reproduces D3D's result. Only flat-colour (untextured) materials actually have non-white diffuse in the data (see Results); `ambi == diff` in 98 % of materials.
- `emissive` (linear RGB, same power-curve conversion as the diffuse) = `emis` when its luminance `0.299R+0.587G+0.114B` (`FUN_1004a8c0` @1004a8c0, weights at 1008ab58/60/68, threshold `_DAT_1009fda8` = 0.0f) is > 0, else 0. Evidence: `FUN_1004ac5f` @1004ac5f sets rs 148 (EMISSIVEMATERIALSOURCE) = `lum <= 0` on every material (so the material's `emis` is only the D3D emissive when luminance > 0; 145/146/147 = 0 = MATERIAL). D3D adds the emissive to the lighting sum **before** texture modulation (`tex * (emis + lighting)`); values in the data are almost always (1,1,1) (fully self-lit: lamps, signs, windows) or small greys, so a renderer should multiply the emissive by the texel, not add it flat (told Renderer3). A per-instance emissive override exists (`RRefFrame_t::SetEmissive` @10045329 → frame +0x8c → `RVisual_t::RenderWithTransparency` @1004d2d8 sets rs 148=1 and passes it in the `_D3DMATERIAL7`); it is runtime state (effects), not in the data, so not emitted.
- `glow_mask` = opaque, textured, and texture stage 0 has COLOROP = ADD (`tst (1,7)`) with COLORARG1 containing D3DTA_ALPHAREPLICATE 0x20 (`tst (2,34)`) — exactly the stage setup of mode 5 of `FUN_10040645` (stage 0 = `tex.a + diffuse(lighting)`, stage 1 = `tex.rgb * stage0`, ALPHAOP disabled, 27=0). Stage layout in the archive: `tstv_count` stages, each `tstm_count` followed by that many `tst_type`/`tst_value` pairs (the members aggregate all elements; order of types within a stage varies). Present in 2964 delta states (1011 + 362 + 1591 with 27=0); the exact engine formula is `rgb * min(lighting + a, 1)`.
- **Cutout blends**: an `AlphaBlend` submesh (rst 27=1, opac 1) whose texture alpha is essentially 0/255 (≤ 2 % of texels in 16..239 — a guess, `CUTOUT_PARTIAL_MAX`) is emitted as `AlphaTest`: the engine blends it (z-write off, sorted) but the result equals a cutout, and avoids per-instance sorted blending. Done in `decode_record_into` (the texture is needed). 347 of 1225 blended submeshes in 1010001 became alpha-test; the remaining 886 have real soft alpha or opac < 1 and stay `AlphaBlend`.
- Not representable in the contract and dropped: `spec/shin/shin_str` (specular, 29 SPECULARENABLE), `env_texture` (268 materials; only drawn when the device has ≥ 2 texture stages and the visual's env flag `+0xe1` is set), detail/secondary texture channels (`tst_*`), node `prio`, z-write state, `anim_matrix`/uv/visibility animation keys. Vertex colours: **no mesh uses them** — every `SimpleMesh` has FVF 0x112 (no diffuse/specular), and rst 145=0 takes the diffuse from the material anyway — so `Vertex::color` is white. `FvfLayout` still skips diffuse/specular bytes if another layout shows up.

### Playfield record (1000001)
```
u32 version (7..10)  u32 id  char name[32]
u32 tilemap id (rdb 1000009)  u32 zone size in tiles (10)  u32 count (zones, or rooms for dungeons)
if version > 8: 5 x i32 + 0x18 bytes (PFWorldX/Z, environment id; not used)
if tilemap id != id: count x room            (dungeon / indoor)
else (outdoor): count x { u32 n, n x camera attractor (vec3 + quat + vec3 + f32) }
room := u8 flags (rot = flags&3, 0x80 = has name)  u8
        u16 x1,z1,x2,z2 (tile rect in the dungeon tilemap)  f32 pos[3] (room centre, world)
        u16 ndoors, ndoors x (u16,u16)   [char name[32] if flags&0x80]
        i32 lightmap size+4, i32 present, [size bytes]
        u32 (n+1)*0x3f1 liquid blocks: n x { u32, u32 n1, n1 x vec3, u32 n2, n2 x 3 u16 }
        if version > 4: u32 n, n x (vec3 + quat + [vec3 if version>=6] + f32)   camera attractors
```
(`n3Room_t` reader N3 @0x10012803.) Rule found empirically over all 601 records: **tilemap id == playfield id ⇔ outdoor heightfield playfield** (325 records; for 324 the statel zones use the outdoor layout, 4622 has its own heightfield but dungeon-style zones); the other 276 are dungeons/indoor playfields built from rooms. After the zones (outdoor: per zone `u32 n` + `n × 44` byte attractors; dungeon: after the rooms) every record has the `RDBPlayfieldAnarchy_t` tail: liquids + environment, see *Liquids* and *Environment* (`Record::tail` = its offset).

### Heightfield tilemap (1000009, `CHGA`)
```
"CHGA" u32 size u32 version(=1) u16 width u16 height   valid size in CELLS (Newland City 150x150)
f32 cell size (4.0 m) f32 height scale (0.2)
u16 n; n x u16 tile index -> ground texture id (1010006/21/22)
u32 (=1), then a Funcom object archive (same member encoding as `## meshes`, but without the version/range header):
  u32 name_count, name_count x {cstr kind, cstr name}, u32 object_count, (object_count+1) x object
  object 1 = AnarchyGroundData: map_width, map_height (vertices = cells+1 padded to whole patches),
  map_modulo, tiletexture_count, heightmap_compressed_data, heightmap_small_data,
  tilemap_compressed_data, [buildingmap_compressed_data], texture refs, tile_type_data
```
*Patches.* `m = min(2^tz(map_width-1), 2^tz(map_height-1), 64)` (`tz` = trailing zeros; DisplaySystem @0x10036f17 and @0x10035966); a patch is `m×m` cells with `(m+1)²` vertices; `(map_width-1)/m × (map_height-1)/m` patches, row-major. The three `*_data` members are concatenations of `u32 length + bytes`, one entry per patch.
*Heights* (`Patch_t::DecompressHeightMap` @0x10035df0): zlib stream of `(m+1)²` bytes (when `heightmap_small_data` is 4 bytes) or `(m+1)²` i16 (8 bytes = four corner heights). The samples are the **second order prefix sum** of the stream — first running down every column, then along every row, wrapping at 8/16 bits. 8 bit data become `byte << 8` (`FUN_10035db8`). The result is an **unsigned** 16 bit height: `y = value / 256 * height_scale` metres (0..51 m at 0.2). **16 bit maps** (`heightmap_small_data` 8 bytes; 22 records: 556, 656, 4364, 4380–4388, 4894, 6001, 6012, 6022 …) store the scale already divided by 256 (0.2..0.5 / 256 = 0.00078..0.002): metres = raw sample × scale for both widths, the loader multiplies those scales by 256 (they decoded flat before; `playfield::tests::statels_sit_on_the_terrain` checks the median statel-terrain gap: 566 0.10 m, 600 0.06 m, 556/656/4894 0.03 m). 4364 and 4380–4388 stay unexplained (statels 5–70 m off the field, correlation 0.2). Verified: correlation 0.90 between terrain height and statel y in 566; heights are continuous across patch borders; vertices outside the valid `width×height` window are prefix-sum padding (vertical streaks) and are not emitted.
*Tiles* (`tilemap_compressed_data`): zlib `m×m` u16 per patch. The tile index is `value & mask` with **mask 0x3fff if the archive has a non-empty `tile_type_data` member, else 0xff** (ctor sets `+0x60`; verified: 325/325 CHGA records have all indices < n with this rule, 182 would violate it with a fixed 0x3fff). Index → texture id via the header `u16` list; every cell is one textured quad (the engine bakes per-patch textures from the same tiles, `FUN_10037957`). Bit 14 of the raw value selects the quad diagonal (`n3RoomSurface_t::GetTileTriangles` N3 @0x10014888: `(tile >> 14) & 1`: 0 → diagonal (x,z)-(x+1,z+1), 1 → (x+1,z)-(x,z+1)); bit 15 is not used by the loader.
*World mapping*: AO x = column × 4 m, z = row × 4 m (statels sit on the terrain with this mapping: all 1090 statels of 566 lie in x −41..592, z 0..599 for a 150-cell = 600 m map). Scene space negates z (see `## meshes`).

### Terrain rendering (`playfield/terrain.rs`, `playfield/shadow.rs`)
*Tile textures* (1010006/21/22, header 24 zero bytes): 417 are JPEG and **432 are RGBA PNG** (Shadowlands tiles — dark ash, lava, snow; alpha is 255 everywhere but one tile). The JPEG-only search that the first loader used left every Shadowlands cell untextured. Many tiles are authored transition tiles (grass blobs on sand, plate borders) — the client has **no blend masks**: 1010022/1010021/1010006 are only the 64/128/256 pixel mip sets of the same art, and `FUN_10037957` (DisplaySystem @0x10037957) bakes the per-patch distance texture by averaging `n × n` tile texels per baked texel (`FUN_100365b2` → tile bitmap, `PixelFormat_t::ConvertColor`), nothing is mixed between neighbouring cells. The original therefore shows the 4 m tile grid.
*Transitions (ours)*: the loader emits one `Mesh`/`Instance` per 64×64-cell patch (frustum culling; `(m+1)²` shared vertices, uv = lattice coordinates, repeat sampler). Base submeshes: opaque, one per tile texture. Overlays: for every cell whose 8-neighbourhood uses another texture, the other textures are drawn alpha-blended (`Blend::AlphaBlend`, alpha in the vertex colour, +1 cm) in ascending texture id with alpha `w_M / (w_T + Σ w_M')` where `w_M(v)` is the fraction of the (up to four) cells around vertex `v` using texture `M`; over the opaque base this equals `Σ w_M · tex_M` at every vertex, so cell and patch borders are continuous (`terrain::tests`). Cost: Avalon (997 600 cells) loads in 0.47 s (0.13 s with hard cells).
*Baked ground shadows* = rdb **1000007** (keyed by playfield id, 323 ids = 320 outdoor + 3 others; `data/Shadows/<id>.sdw` are older copies of the same format): `u32 end[6]`, six 8 bit grey PNGs (blob 0 starts at byte 24, blob i at `end[i-1]`, the last `end` is the record length), all the same size `((verts_x-1)/2 padded) × (verts_z-1 padded)` — one texel per two vertices along x and one per vertex along z (Newland City 193×193 vertices → 96×192; Avalon 897×1537 → 448×1536; Varmint Woods 1537×897 → 768×896; verified by overlaying the height map: the 566 crater and plateau and the 600 river valley coincide with dark/flat regions of the map). Values are 4 bit levels × 17 (51…255). The layers are the sun positions of `DayTimeForGroundShadows`/`UseGroundShadows` (DisplaySystem strings): layers 0 and 4 are dark (low sun), 2 is the brightest (mean 160 in Varmint Woods vs 82/129/129/82), layer 5 is flat dark. The maps contain hill shading *and* cast shadows (every tree and building). We bake layer 2: vertex colour `= 0.35 + 0.65 · min(texel / p90, 1)` (`SHADOW_FLOOR`, `p90` = 90th percentile of the layer; the client's lightmap blend is not known). Geometric normals stay (the renderer flips normals facing away from the eye).

### Statel file (1000003)
```
u32 version (=1)  u32 offset[count]  (count = record count; zone/room i = [offset[i], offset[i+1]), last to end)
global section (only if offset[0] > end of the table): u32 v; if v != 4 { u16 n; n statels; 2 x {u16 n; n x 18 byte fog/sound entry} }
outdoor zone (tilemap id == id):  u16 k; k x u16; 4 x { u16 n; n x statel }; u16 nlights; lights
dungeon zone (room):              u32 size; size bytes (compressed room index list); 2 x {u16 n; n x 18 byte entry};
                                  2 x { u16 n; n x statel }; u16 nlights; lights
statel := f32 x,y,z  u32 flags  u32 mesh id (rdb 1010001; 0 = none)  u8 scale  u8 nattr
          nattr values encoded as (u32 mask; one u32 per set bit) repeated until nattr is consumed; [u32 colour if flags & 4]
light  := f32 x,y,z  u32 flags  u8 type,r,g,b  [if (type&0x1f) in {2,4}: u16 range, u16 a0, u16 a1, u16 a2, (type 4: u16 inner, u16 outer)]
```
Readers: `n3StatelLoader_t` run function N3 @0x10028029, `FUN_10027f16`/`FUN_10027cb2` (zone headers), statel reader `FUN_1002777a`, light reader `FUN_10026e66`, global `n3StatelController_t::ReadGlobalData` @0x100250ac / `ReadStatelIndices` @0x10026191. Outdoor zone i covers tiles `(i % w, i / w)` of `zone size` tiles (566: 15×15 zones of 10 tiles = 40 m); statel coordinates are absolute world coordinates. Dungeon zone i belongs to room i: global = `room.pos + Ry(rot·90°)·local`, orientation `Ry(rot·90°)·R` (`FUN_100271b6`). Every zone of all 600 statel records parses with exactly one of the two layouts (outdoor ⇔ tilemap id == id, except 4622).
*Orientation* (`FUN_1002777a`): `u = flags >> 7`. If `flags & 1 == 0`: `heading = (u/180 % 360)°` about Y, `pitch = (u%180 − 90)°` about X, `roll = (u/180/360)°` about Z, `R = Rz·Rx·Ry`, uniform scale `scale/100 + 0.1` (byte 90 → 1.0). If `flags & 1` (~0.5 % of statels): heading `(u % 630)/630 turn`, stretch `k = ((u/630) % 211)/100 + 0.5`, shear `t = ((u/630)/211)/100 − 1.25`. The decompile builds an *anim matrix* `M = identity; FUN_10026cdc(M, 1, 1/k, 1/k); FUN_10026d5c(M, t, 0)` (row-vector form `[[1, t, 0], [0, 1/k, 0], [0, 0, 1/k]]`: `FUN_10026d5c` adds `t·column0` to column 1 of every row — a **shear of y by x, not a translation**; the old note called it a translation term), attaches it with `VisualMesh_t::SetAnimMatrix` (applied before scale/rotation, see `UpdateWorldMatrix`) and uses uniform scale `s·k` with `s = scale/100 + 0.1`. Linear part in column form: `R · [[s·k, 0, 0], [s·k·t, s, 0], [0, 0, s]]` (`statel::orientation`, fixture test `stretch_shear_form`). Constants read from N3 `.rdata`: 2π (`DAT_1003e638`) / 630 per heading step (`DAT_1003e660` = 0.0099733), 0.5 (`DAT_1003c868`), 1.25 (`DAT_1003e658`). Rotations are right-hand-rule numerics in AO's left-handed space (`FUN_100014e4` is the textbook Hamilton rotation, `FUN_10003dc3(a,b)` computes `b⊗a`); e.g. flags 0x2d00 = identity, heading 90° maps +z to +x. Verified visually: Omni-1 Entertainment avenues and building rows line up at 45°, Newland City walls enclose courtyards.
*Scene transform*: `M_scene = F · (T·R·S) · F`, `F = diag(1,1,−1)`, matching the z negation baked into the meshes.

### Statel lights (`playfield/statel.rs`: `Light`, `scene_light`)
Reader `FUN_10026e66` (N3 @0x10026e66) builds a `VisualMesh_t` carrying a light: `VisualMesh_t::SetLight(rgb/255, type & 0x1f, range, a0, a1, a2, in, out)` (DisplaySystem @0x1006b6b0) → `RLight_t::RLight_t` (randy31 @0x1003fd4a) whose 0x68 byte `light_info` block (+0xa4) **is a `D3DLIGHT7`** (type, diffuse, specular, ambient, position, direction, `dvRange` +0xf0, `dvFalloff` +0xf4 = 1, `dvAttenuation0..2` +0xf8/0xfc/0x100, theta +0x104, phi +0x108; `render_t::SetLight` @0x10021815 hands it to `IDirect3DDevice7::SetLight`). Type mapping (`FUN_1003fcbe`): data type 2 → `D3DLIGHT_POINT`, 4 → `D3DLIGHT_SPOT`, 1 → directional (not in data). Decoded values: `range` = raw u16 metres; `a0 = u16/100` (`_DAT_1003d5a0`), `a1 = u16/10000` (`_DAT_1003d150`), `a2 = u16/1e6`, or `u16/1e4` when type bit 6 is set (`_DAT_1003e640` / `_DAT_1003e644`); spot angles = `u16 * 2π/360` rad, and `RLight_t::SetSpotAngles` (@0x1003fcde) doubles them (`_DAT_10093998` = 2.0) into theta/phi; spot direction = local +X rotated by `flags >> 7` decoded exactly like statel heading/pitch/roll. **Type byte**: bit 7 → the function returns null and no light exists (`if (-1 < (char)type)`: 130/132/194/196 = 1 805 of the 10 083 records parsed are dead), bit 5 only selects the statel's group-mask kind (`FUN_10024455`, not visual), bit 6 the `a2` divisor. `RVisual_t::CullLights` (randy31 @0x1004ce96) only enables lights with `dvRange > 0` (and a sphere test against the visual); at most 8 lights per visual (`SetMaxActiveLightCount`) — the static-light grid in `ao-render` plays that role. Positions are zone/room local and use the statel placement (room rotation + `room.pos`); `Scene.lights` is in scene space (z negated).

*Contract mapping* (`statel::scene_light`, **calibration guesses**, the contract is linear): D3D intensity `I(d) = 1/(a0 + a1 d + a2 d²)` for `d ≤ range`. Effective range = first `d` with `I < 0.05` (≤ `range`); peak `k` = least-squares fit of `k(1 − d/R)` to `min(1, I(d))` capped at 1 (the 8 bit framebuffer saturates; unclamped I reaches 20); colour = `(k · rgb/255)^2.2` (the client calculates on gamma values, same convention as the ambient colour). Spots have no cone in the contract: they become point lights shifted along their axis by `R/2 (1 − sin(outer half angle))` with the range reduced by the same amount. Results (`pf_stats`, all 601 load): **8 278 lights in 310 playfields** (most: 362 SL ACG 413, 321 353, 125 264, 127 258, 4347–4349 168); lights lie within 60 m of the scene bounds in 127/362/566 (test). Screenshots: dungeon 127 (red light at (185,115,−225): red tint on the vault ceiling; corridor lights lift the floor/walls by a visible margin versus none) and Newland City 566 (warm lamp at (391,34,−304) warms the pavement); the baked room lightmaps of dungeons (`depack_lightmap`) are separate.

### Spawn point (`playfield/spawn.rs`, `dungeon::entry_spot`)
No record names an entry point (the server tells the client where a character arrives; grids/whompahs are not distinguishable statels — statels carry no names and their attributes are zone ids), so `scene.spawn` / `spawn_look_at` are chosen from content:
* **Outdoor**: densest 3×3 block of 32 m buckets of statel boxes (boxes > 150 m, skydomes, are ignored); the first ring position (8 m steps, 12 directions) around the cluster centroid whose 4 m eye column is not inside a statel box, eye = terrain + 4 m; look at the heading (16 candidates, ±40° cone, 15–250 m) with the most statels whose first 15 m and terrain profile are clear. Solid city blocks with no free street position hover 12 m over the tallest box. Terrain-only maps hover 25 m over the map centre. 566 now opens in the Newland City park, 705 on the Omni-1 Entertainment plaza, 505 in the Avalon desert.
* **Dungeons**: rooms named `entr…/lobby/start…/enter…` first (49 playfields have one, e.g. 127 "Entrance Stairs"), else file order. Rooms over 400 floor cells (e.g. The Grid 152) use the cell nearest the centre and look at the room's props; other rooms use the cell with the longest open run along an axis and look down it, eye 1.7 m above the interpolated floor.
* The 6 playfields with 0 rooms and a 4 byte statel file (1424, 1673, 2006, 2014, 2024, 4352) are empty in the data and have no spawn.
`pf_stats` checks every playfield: spawn and look-at present, spawn inside the instance bounds, terrain/floor 0.5–30 m below it (`floor_below` = highest fixed-geometry triangle under the eye), look-at not straight above/below.

```
u32 n; n x { u32 kind, u32 nv, nv x f32[3] (AO world x,y,z), u32 nt, nt x u16[3] }     liquid polygons  (n3WaterData_t)
u32 0, u32 0, u32 size (=30)  26 bytes EnvironmentData_t                                (see Environment)
```

Parses for all 601 records (325 outdoor: 5 746 polygons + 143 empty ones; the 276 dungeons have none). `n3Zone_t::SetWater` (N3 @0x1001abf2) keeps the highest water level per zone (`CalculateWaterHeightMax` @0x1000c84c). `kind` is the `VisualWater_t::Create` liquid type (DisplaySystem @0x1003ad24): bit 0 = sloped/flowing polygon, `kind >> 1` selects the liquid. `FUN_100b7273` (Gamecode, camera inside a liquid) shows the colours: `AddFog(r,g,b,density)` with `kind>>1` = 0 (and 5, 6, 9) water `(0.1,0.3,0.25)`, 1 lava `(1,0,0)`, 2 slime `(0.062,0.114,0.065)`, 3 acid `(0.154,0.991,0.02)`, 4 mud `(0.2,0.1175,0.0545)` (floats at Gamecode 0x10160810…0x10167e78). Types seen by playfield: lava 3 in Burning Marshes 4005 / Inferno 4605 / Three Craters West 6101; kinds 14, 16, 338, 960 (a few playfields) fall back to water.

### Environment (`playfield/environment.rs`)
`GameData::EnvironmentData_t` (26 bytes, `operator>>` GameData @0x1000b711; the stream order swaps bytes `0xa`/`0xb`). Gamecode `FUN_100bd183` copies bytes `0..7`/`8..0x12` to the sound/weather object (not decoded) and bytes `0x13..0x19` to the atmosphere object that `FUN_100bd661` runs every frame: `VisualAmbientLight_t::AddAmbientLight(b[0..3]/255)` and `VisualFog_t::AddFog(b[3..6]/255, b[6]/100)` (divisors 255.0 @0x10166f60, 100.0 @0x10158670; all 601 records have size 30). So **ambient = bytes 0x13..0x15, fog colour = 0x16..0x18, fog density = 0x19 %**. Black fog colour → default grey 0.2 and density 0.01. `VisualFog_t::process` (DisplaySystem @0x10058443): fog end = `far - (far - near - 5) * D`; `Randy_t::SetFogParameters` (randy31.dll @0x10041876) programs D3D linear vertex fog `[near, end]` (the density argument is unused). Examples: Varmint Woods 600 fog (68,232,107) 15 %, ambient 50; Avalon 505 fog (250,250,250) 2 %, ambient 50; Newland City 566 ambient 100, no fog colour. Over 601 records: ambient grey 30 (312 records), 40 (66), 0 (44), 70 (41) …; density 0 (335), 10 % (89), 5 % (50), 15 % (36), 50 % (30). Statel fog volumes (`n3StatelController_t::StatelFogRun` N3 @0x10024dbc: colour bytes `0xe,0xd,0xc` = R,G,B, `0xf` intensity, `u16` radius at `+0x10`, density ∝ `1-(d/r)²`) add to this fog; they are still parsed over.

### Sky, sun, time of day, view distance (`playfield/sky.rs`, `environment.rs`)
The client has **no sky data in the playfield records**: the sky is a set of FXS tweak objects loaded from `cd_image/twk/*.txt` (`Tweak_Playfield_<id>.txt`, else `Tweak_Playfield_OutdoorDefault/IndoorDefault.txt`, which `!include` `Tweak_Rubi-Ka_{Atmosphere,SunLight,Sun,Horizon,ThickClouds,SingleClouds,Moon1..3,DotStars}.txt`; Shadowlands `Tweak_Shadowlands_*`; indoor: `Tweak_BlackBackground` + `Tweak_Rubi-Ka_IndoorLight`). RE evidence: `GfxVisualSkyrise` / `_GfxControlSkyRise_t` (Gamecode @0x100ef7a5) is the effect-object path, but the Rubi-Ka sky is plain tweak script. Expressions evaluate **left to right** (`This.CloudScrollX + GAME.HighAltitudeWindX % 1` only makes sense that way).
* **Time**: `Tweak_GAME.txt`: `GameDayTime` (written by the game, 0..27·60·4 = 6480), `DayTimeFactor = GameDayTime / 6480` indexes every colour track, `DayTimeForGroundShadows = GameDayTime * 15`. The server clock is not available offline; we evaluate at `Tweak_GAME_FrozenTime.txt` (the client's fixed-time debug setting): `CurrentDayTime 2648.69` (factor 0.409), `Sun1Rotation q(0.900351, -0.0951056, 0.344078, 0.248863)`; `TweakedSunDirection = (0,0,1) [ROT] Sun1Rotation` read as (w,x,y,z) gives (0.57, 0.34, 0.75), a sun 20° above the horizon, the only order that keeps the sun up [INFERENCE]. Array indexing between entries is linear over `f·(N-1)` [INFERENCE: FXS array access not decompiled].
* **Atmosphere** (`Tweak_Rubi-Ka_Atmosphere.txt`): camera locked 6 vertex strip (y 0 @ z 1000 → y 400 @ z 200 → y 400 @ z −500, `ZFUNC ALWAYS`, no z write, `FOGENABLE` on) with vertex ARGB = `ColorBottom{I,R,G,B}[t]` at the horizon and `ColorTop…` above (27 entries; Shadowlands 8). We emit a camera centred dome (`Scene.sky`, radius 400, renderer pins it to the far plane) whose vertex colour reproduces the ramp per elevation (`s = 1000 tan e / (400 + 800 tan e)`, top colour above 63°), × I, and bake the fog of the strip's distance into it (the renderer draws sky unfogged).
* **Fog tint**: `AddFog(R,G,B,0.025)` with `AddFogIntensity = (BottomI + MiddleI)/2`, `AddFogR = (BottomR + MiddleR)/2 · intensity`. `VisualFog_t::AddFog` (DisplaySystem @0x1005820c) keeps a running weighted mean: `new = (d·c_new + D·c_old)/(d + D)`, density `D = max`; the record's fog (`environment`) and the atmosphere's are mixed that way (Newland City turns dusty beige, Varmint Woods stays the record's green). `VisualFog_t::process` (@0x10058443): `end = far − (far − near − 5)·D` only when `far − near > 5`, so density 100 % gives `end = near + 5` — pf 4524/6055 are a white-out in the client too (the sky dome is fully fogged, no seam).
* **Light**: `Tweak_Rubi-Ka_SunLight.txt`: `GroundLightCurrent = min(GroundLight[t] · 2, 1)` is the sun colour (replaces the old `1 − ambient` guess), `AmbientLight[2] = 40/255, 128/255` / Shadowlands `AmbientLightR/G/B[2]` compete with the record ambient (`AddAmbientLight` = per-channel max, DisplaySystem @0x10059d2c). Indoors `IndoorLight`: ambient 0.01 vs the record ambient, no sun.
* **Time of day API**: `load_playfield_at(store, dir, id, day_time)` (`aomac view pf <id> --time-of-day <s>`, 0..6480; 0 midnight, ~3240 noon); `load_playfield` = frozen 2648.69. The time drives the colour tracks, ground shadow layer, fog tint and the layers below. **Sun ephemeris [FIT]**: the game's `GameSun1Rotation` is not stored; the sun runs a great circle, one turn per day, with horizon crossings at factor 0.525 ± 0.25 (the `GroundLight` tracks switch on ~0.27 / off ~0.79) through the frozen sample, which gives a noon elevation of ~27° (sunrise ≈ t 1750, sunset ≈ t 4990). Sun 2 keeps its frozen 13° offset from sun 1 in sun 1's azimuth/elevation frame [INFERENCE]. `GAME` values the game writes per frame (wave curves, wind, delta time, the `Counter` integrators) are 0: still frame.
* **Generic object layer** (`sky/script.rs`, `sky/layers.rs`): `Object` blocks of the flattened script are parsed (fields, every `Expansion` block active, `RenderState`/`TextureStage`/`Texture` of the `StateBlob`s), expressions evaluated left to right, rotations as `v(axis), degrees` / `q(w,x,y,z)` / `a [ROT] b` (apply `a` first). Layers are emitted in `BackgroundSort` order (Tweak_Rubi-Ka_ObjectSort): Universe 2, DotStars 3, Moon1-3 4-6, Atmosphere 7, Moon*_Close 9-11, BattleStations 12, Sun 13/14, ThickClouds 150, SingleClouds 250, Horizon 428; only `Priority e_RenderPriority_PreRendering` objects (the spaceships are `Normal`). All are camera locked with `ZFUNC ALWAYS`, so only order and angular size matter. The atmosphere is now alpha blended with vertex alpha = its `I` track (opaque by day, transparent at night), so stars/moons behind it show at night; moons sorted after it (`Moon*_Close`, additive, `MODULATE2X`) stay visible by day.
* **Universe / DotStars**: `Universe` mesh `star_dome.abiff`, overridden by `Expansion BP01` to `nebulas_sphere.abiff` (a belt of radius 93, |z| ≤ 33, so it is a band with a hard edge, not a full sphere). Dot size (0.2° quad) and the random seed are guesses.

* **SingleClouds** (`e_SingleCloud`, `Altitude 100`): `FUN_100601dc` @DisplaySystem only builds the material table (`single_cloud01..04.png`, `clouds3`, `stars01`, ...); the placement code was not found, so 32 billboards (260 × 130 m) are scattered pseudo randomly at 150–900 m, 100 m up **[GUESS]**.
* **Horizon**: `horizon_object.abiff` (200 × 200 dish, y −16..0, `horizon_object_v01.png` = top down map of the continent), `ScrollMatrix` offset = `(OffsetFromHQ_X / 51200, OffsetFromHQ_Z / −51200)` with `OffsetFromHQ` = `PlayfieldData.UniversePosition` (`RKPP.<name>` of `Tweak_RubiKa_PF_Positions`) − `RKPP.Omni_1_HQ`; the camera's offset inside the playfield is not tracked. ### Dungeon rooms
Code: `playfield/dungeon.rs` (`parse_gnda`, `parse_piece`, `Gnda::compute_cells`, `build_room`). A room shell is **not stored as a mesh**: the client (`n3GroundRenderer_t::CreateDungeonRoom` N3 @0x10008563) stitches prefabricated cell meshes chosen by an autotiling pass over the dungeon tilemap and bends them with two height layers. Everything is evaluated per cell of the room's `rect` (`[x1,z1,x2,z2)`, image rows = z).

**`GNDA` tilemap** (`RDBTilemap_t::ReadBlob` DisplaySystem @0x10078391, header reader `FUN_10077aaa`; 111 records, ids 121…):
```
"GNDA" u32 size u32 version(=1)  u16 w u16 h (280)  f32 cell size (2.0)  f32 height scale (0.2)
u16 n (<=32)  n x u16 tile id (ids[0] = 0 = empty)
n x { u8 a, u8 b,  a x { u16 neighbour tile id, 16 x u16 mesh id },  b x u16 }        b is always 0 in the data
sections { tag[4] u32 size(incl. 12 byte header) u32 version, payload }, padded to 4 bytes by `size`:
  DCGA PNG L8   tile index per cell (bits 0..6; bit 7 = "partition/door" flag); 0 = no cell
  DHGA PNG L8   floor height  (x height scale)           HCDA PNG L8  ceiling stretch (x height scale; client stores +0x20)
  IRHA u32[]    door edges: v>>1 = cell, v&1 = 0: edge to x+1, 1: edge to z+1 (both cells get the door bit)
  TAHA u16 k, k x {u8 tile, u8 c, c x u16 mesh}, then PNG L8: per cell override: (value>>2) selects list[value>>2 - 1]; value&1 door-frame side hint, value&3==2 = plain floor
  XTHA u16 m, m x u16 (version 1) | u32 (version 2) material ids, [u16 layer count (18) unless a PNG follows], ceil(layers/3) RGB PNGs = `layers` material indices per cell (R,G,B = layers 3i..3i+2)
  HSTA  u16 tile heights /10 (only used for room height bounds)
```
*Mesh table.* The 16 words of a neighbour row go to table slots `0..4, 6..15` (stream word `k < 5` -> slot `k`, else `k+1`; word 15 is dropped, slot 5 is never read from the file). Slot 5 of the *self* row (`table[t][t]`) is the tile id: **the flat floor+ceiling piece of tile `t` is mesh id == tile id**. Slots 0..4/6..15 of row `[t][0]` (walls against the void) correspond to the autotile keys below, shifted by one (`slot = key index`, key index 1-based in `KEYS`).

**Cell meshes** (rdb **1010013**, 363 records, `RDBMesh`-like object `FUN_1006ee4e` DisplaySystem): `u16 count`, `count` x { `u16 n`, n x 32 byte vertex (pos, normal, uv f32), `u16 index count`, indices u16 }, then 12 zero bytes. Block `i` is drawn with the material of layer `i` of the cell (block 0 = floor quad at y=0, block 1 = ceiling quad at the room height 4/8/16/32/100 m, further blocks = wall levels of 4 m; empty blocks have `n = 0`). Pieces are authored in a 2×2 m cell, y up, wall slab on −z.

**Autotiling** (`FUN_100169ab`, N3 @0x100169ab, dungeon branch; sweep over image rows from the last to the first, x ascending). Per cell with `tile = DCGA & 0x7f != 0`: mask `m` bit0 = z+1 empty, bit1 = x+1, bit2 = z−1, bit3 = x−1 (empty = tile 0). Walls added towards a flagged (bit 7) partition neighbour are carried to the neighbour cell (`up`/`left` carries; carry = 0 when the cell has a wall on that side): `flagged(x,z) && flagged(x,z+1)` -> bit1, `flagged(x,z) && flagged(x−1,z)` -> bit2. A door-edge cell with a wall bit whose neighbour across it is also a door cell gets flag `0x10`; with `TAHA & 1` the frame variant `0x30/0x50/0x70` follows from the TAHA bits of the neighbours (jamb left/right/both). Key = min over 4 right-rotations of `m & 0xf` (`n` rotations -> rot), `| (m & 0x70)`; slot = index of the key in `KEYS = [0f 07 05 03 01 00 31 51 71 1d 33 11 0f 1f]` (N3 `DAT_1005bce0`) + 1; `nb` = 0 if `m != 0` else the tile itself; mesh = `table[tile][nb][slot−1]`; keys 00 (flat), 01 (single wall), 03 (corner), 11 (lintel), 31/51/71 (frame with jambs) are the used ones; 05/07/0f (corridor, dead end, closed) have no mesh in any record (87 corridor + 8 dead-end cells of ~676 000 cells in all dungeon rooms), those cells get the floor only. Rotation angle of the piece about +Y: `rot·90° + 180°` (Hamilton rotation as in `statel::ry`): bit0 -> wall on +z, bit1 -> +x, bit2 −z, bit3 −x. If block 0 of the chosen piece is empty the flat floor piece (block 0 only) is added.
*Corner posts* (`DAT_1003d718` = `[0f 09 03 01 06 00 02 00 0c 08 00 00 04 …]`): each cell claims the corner(s) away from its walls (corner 0 = −x−z, 1 = −x+z, 2 = +x+z, 3 = +x−z); a claim on corner 1 is cancelled together with the claim of the cell at (x−1, z+1) on its corner 3, a claim on corner 2 with corner 0 of (x+1, z+1); remaining claims place mesh `table[tile][0][13]` (key `1f`) rotated by `corner·90° + 180°`. Net effect: posts fill the notch at concave room corners.

**Vertex warp** (`DungeonMesh_t` @0x10001a91 / `FUN_10001c3b` N3 @0x10001c3b): cell-local position `p` is rotated, then `u = x/cell + 0.5`, `v = z/cell + 0.5`; `y' = y + F(u,v) + 0.25·y·C(u,v)` with `F`/`C` the bilinear patches over the DHGA·hs (+ `−floor_min`) / HCDA·hs values of the corners `(x−1..x, z−1..z)` of the cell (heights live on cell corners); normals get `n −= n_y·(∂F + 0.25·y·∂C)` with the Catmull-Rom slope polynomials `FUN_100023ad/10002479/1000244e/1000251c` (ported literally, `slope`/`eval_*`). `floor_min` = lowest `DHGA·hs` of the room's cells (`RDBPlayfield_t::CalculateRoomHeights` N3 @0x1001bd82). Vertex welding and the border clamp: see *Welding* below.
*Placement*: cell `(x,z)` centre = `((x−x1)·cell − W'/2·cell, …)` with `W' = ((w−1) & ~1) + 1` (`w = x2−x1`; same for z), then `room.pos + Ry(rot·90°)·local` — identical to statels. Verified: over 173 361 statels of 2000 rooms the 10th percentile of `statel.y − (DHGA·hs − floor_min)` is exactly 0.0, and props lie inside the shell footprint (e.g. 127 room 4: shell x −10..8, props −10..8).
*Materials*: `XTHA` material id `m`: `m & 0x80000000` -> texture rdb **1010004**/`m & 0x7fffffff`, else rdb **1010009** (both JPEG; 1010016/1010017 and 1010023/1010024 are the lower mip sets).

**Evidence.** `aomac view pf 127 --screenshot` (Condemned Subway): the 46 rooms line up into the subway network (corridors meet at doors with the stored rotation), Ladies' Room shows tiled walls with baseboard, sink/mirror/stalls props on the walls, partition with a doorway (IRHA + flagged row), Grand Dome with vaulted ceiling, pillars and the doorway into the restroom; 346 ACD Omnilab (72 separate lab modules, corridors with lit floor strips), 1406/1211 apartments (room + props); concave corners have posts (crack seen before the corner pass). Tests: `playfield::dungeon::tests` (fixture GNDA with PNG sections, piece format, autotile/corner/door states, placement + z mirror + winding) and a real-data build of playfield 127.

**Welding** (`FUN_10001645` N3 @0x10001645, called once per material block of every cell piece right after the warp; `weld_block`). For the new block it (1) hashes positions at 30 cells/m (`DAT_1003c8a8`) and looks for earlier vertices of the same material in the 3×3×3 neighbourhood with squared distance ≤ 0.001 (`DAT_1003c8a0`), squared normal difference ≤ 0.2 (`DAT_1003c898`) and uv difference an integer ±0.1 (`DAT_1003c890`), (2) picks **one integer uv offset for the whole block** (the first offset found for two different vertices, else the last found), adds it to every uv of the block so tiled textures continue across cells, and (3) drops block vertices that now coincide with an earlier one (indices are redirected, collapsed triangles removed). It never averages normals — it is a dedupe plus uv alignment, so it does not change the picture (A/B screenshots of 127/386/331 with and without welding differ in ≤ 6 px by more than 24/255) but cuts the shell vertex count of Condemned Subway (127) from 184 561 to 111 643 (−39 %; first attempt with a plain per-vertex merge broke the floor uv, see the offset step). *Border clamp:* the 4×4 height window gather in `FUN_10001c3b` replicates the nearest valid row (row < 0 copies the next row) and shifts the valid columns left when `x < 2`, i.e. clamp-to-edge = `Gnda::at` (test `height_layers_clamp_at_the_map_border`); the old note about an unported `local_2c` clamp was that vertex counter, not a clamp. *Cracks:* between pieces the warp is continuous (shared corner heights); the remaining unmatched edges are wall-slab ends and doorways (cave-style dungeons, e.g. 331/386, show sky through door openings by design); 160 room interiors of 127/346/331 were rendered and scanned for background-coloured pixels, the only thin (≤ 2 px) leaks are 5–30 px per view at door frames/ledge ends.

**Gaps.** Not ported: liquids, key variants `1d/33` with unreachable canonical masks, per-tile `b` random floor variants (never present), door frames whose key (`canonical|flags`) is not in `KEYS` (e.g. door on a 2-wall cell: no piece, floor only). Room textures use the highest mip set (1010009/1010004). Ceilings are drawn (two-sided renderer): from above, dungeon interiors are hidden — fly inside (`aomac view pf <id> --eye … --at …`).

### Record types
- `rdb_1010002` (770): a complete skinned model = texture table + `CATMesh` stream (skeleton, materials, weighted vertices). Player bodies (ids 5900 athrox m, 5907 solitus m, 5914 opifex m, 5921 nanomage m, 5927 solitus f, 5934 opifex f, 5941 nanomage f – named by their `*_<race><sex>_default.png` textures; later ids add trenchcoat/armour variants), NPCs, creatures, mechs, chairs. 167 distinct skeletons.
- `rdb_1010027` (8): same container and ids as eight 1010002 towers (`maintower`, `Bone01_Main`, …), ~3× fewer triangles — the low-detail proxy, as 1010026 is for 1010001. (Its 32-byte name field holds the root-bone name followed by float garbage, like the others.)
- `rdb_1010003` (3190): one animation clip each; fits every model whose skeleton hash is equal (898 clips fit the human `Bip01_ac` skeleton, hash `0xbd945cbe`). The clip record carries no name, but the client's name table (below) does: 3168 of 3190 clips are named `<set>_<role>_01_01.ani` (`athrox_walk_01_01.ani` = 10078, `male_idle-stand_01_01.ani` = 10173). Example: 9382 is `athrox_sneakcool` (2.5 s, right foot at 600 ms, left at 1100 ms), **not** the walk as earlier notes had it.
- Heads, hair and other attachments are **not** in these records: they are ordinary static meshes (`rdb_1010001`, see § meshes) mounted on an attractor, see below.

### Model record (1010002 / 1010027)
```
char[32] root          NUL-terminated root-bone name, rest is padding/garbage (0xCD or floats)
u32 marker             (parts + 1) * 1009
parts x { char[32] material_name; u32 texture; u32 env_texture; u32 alpha_aux }   44 bytes, same order/names as the materials
u32 ?                  varies (0x05010500, 0xffffffff, …); not read by the stream reader, ignored
CATMesh stream:
  u32 4 (magic), u32 version = 0x104 (0x67 also accepted by the engine, has no bind positions; absent in the data)
  u32 signature        skeleton hash, compared with the animation's by CATRender_t::SetAnim @10053fe2
  f32 ×2               unused
  u32 n_mat × { string name; u32 flags; string texture_file; [string env_file if flags & 2]; f32 ×15 }
  u32 n × f32 ×4       header-level records (always 0)
  u32 n_bone × { string name; f32 scale; u32 n_child; u32 child[] }        bone 0 is "-nobone-"; hierarchy via child lists
  u32 n_group × { string name ("-noselgroup-");
       u32 n_sub × { u32 material; u32 n_vert × vertex(68 B); u32 n_idx; u16 idx[] }      triangle list, D3D clockwise-front
       u32 n × { f32 x y z radius; u32 bone }                                              collision spheres
       u32 n × { string name; f32 ×8 (pos xyz, quat xyzw, scale); u32 bone } }             attractors
  trailer: 12 zero bytes (769/778 records) or a progressive-mesh LOD table (`vertex_reorder`, `indices`, `neighbours`, `num_splits`, `splits`, `catindices`; 9 records), ignored
vertex = { f32 local0[3]; f32 local1[3]; f32 bind[3]; f32 normal[3]; f32 uv[2]; u32 bone0; u32 bone1; f32 weight }
```
- **Skinning** (`FUN_100543bc`): `pos = w·(M[bone0]·local0) + (1−w)·(M[bone1]·local1)` with `M` the animated 3×4 world matrix of the bone; for `w` above a constant (~0.99) only `bone0`. The stored normal is **bone-local** to `bone0`: `n = R[bone0]·normal`. `bind` is the position in the bind pose; the file has no bind matrices, but `bind = R·local0 + t` holds exactly for every vertex fully weighted to a bone (residual 0 on all bones with ≥3 non-collinear such vertices), so `character::bind_frames` recovers each bone's bind frame from a 3-point frame fit and the bind-pose normals are `R_bind·normal`. Verified: 796 of 798 test triangles of 5900 have the CCW geometric normal agreeing with `R_bind·normal` (raw normals: 370 of 798).
- **Bone matrices** (`FUN_100540a5`): `world = parent ∘ (R(q), scale·t)` with the standard column-vector quaternion matrix (the engine stores its transpose for D3D row vectors; verified: the fitted bind local rotations match the animation's `R(q)`, not its transpose or conjugate, mean 15° over 60 arbitrary clips and 4.7° for the best one) and `scale` = product of the ancestors' `Bone::scale` (1.0 for humans; opifex 5914 has 0.77/0.91/1.50 on root/pelvis/spine, i.e. the shared human clips are re-proportioned by the mesh). The bind-pose translation of every bone equals the animation's constant translation to 4 decimals (e.g. Spine3 −0.1731, 0.0002, 0).
- Bones without a track in the clip keep identity rotation and zero offset (the engine's defaults).
- **Rest lengths differ per clip set** (found via `aomac view char 41664 --anim 9375`: forearms/hands/feet float away, bind pose fine). `FUN_100540a5` (decompiled again, @100540a5) applies the clip's translations literally: `t_local = anim_t · accumulated Bone::scale`; bone modes 1/2 in the engine's per-bone table (`this+0x20`) are controller hooks (default 0), not data. Clips of the same skeleton **hash** need not share bone lengths: the three sets `athrox`, `male`, `female` carry their own, e.g. for skeleton_solitus (41664, name table) the bind UpperArm offset is 0.118 m against 0.166 m in `athrox_*` clips (bind and clip offsets agree to 5 digits only within the model's own set: 5907/`male` 0.26302 vs 0.26302). So a model must be posed with its own set (`character_animations`/`role_anim`; models no set is named after, such as `skeleton_solitus`, get the set with the smallest `pose_detachment`, here `male`). `pose_detachment(store, id, anim, t)` = max over parent/child bone pairs of (nearest distance between the two bones' rigid vertices posed − in bind): 0.005–0.05 m with the right set (5900/`athrox` 9375 0.005; 5907/10191 0.014; 41664/10191 0.033), 0.13–0.18 m with another set (41664 + 9375/9382/10078 0.13, 5907 + athrox clips 0.16). A bind-length retarget factor per bone (`|bind offset|/|clip offset|`) was tried and dropped: it fixes the cross-set pose (0.17 → 0.03) but breaks Atrox (0.005 → 0.08) because several fitted frames are exact for their vertices without being the joint, and it is not what the client does. char_stats prints the metric over 763 models with their own set: worst 0.357 m (hellhound 29902, a large animal; screenshot intact), 16 above 0.15 m, all large creatures/wing flappers that were inspected as intact (29902, 16777).
- **Materials** (`RMaterial_t` ctor @10041043; float order = `FAFMaterial_t` members): diffuse, specular, ambient, emissive RGB, shininess, shininess strength, opacity. `flags & 8` ⇒ the texture's alpha channel is *not* transparency (`IsAlphaUsedAsTransparency = !(flags>>3 & 1)`; always together with `alpha_aux = 1` and mostly RGBA PNG: 536+84 of 685 `alpha_aux = 1` PNGs; glow/spec masks); `flags & 2` ⇒ env-map file name follows; bit 0 and 2 are not used by the ctor. Not used here: the `texture_file` names (`body_athroxmale_default.png`) – the rdb ids in the part table are authoritative (`ents[i].name == materials[i].name` for all 778 records).
- **Textures**: `parts[i].texture` = `rdb_1010004` id (JPEG or PNG; 3738 parts: 9 without id, 8 ids not in the database). Seven 1010004 records (shared by 178 character materials) start with `02 00 00 00 0D 0A 1A 0A` instead of the PNG signature; the remainder is a valid PNG, `texture::decode_texture` repairs them. `hands_*_default.png` (e.g. 9235) is a solid green (0,255,0) 128×64 placeholder, as is Atrox's `head_athroxmale_default.png` (9232, on a 3-vertex/1-triangle `head` part). Player bodies are re-skinned from rdb **1010011**, see § Name table, animation roles, player characters. (Gamecode.dll's `COMMAND_DEBUG_SKIN_{HANDS,BODY,FEET,ARMS,LEGS}` GM key bindings in GUI.dll name the same five skin slots; the swap itself is an inference from the table names, the substitution code was not decompiled `[INFERENCE]`.)

### Animation record (1010003)
```
char[32] root; u32 n_event; n_event × { u32 time_ms; char[32] name }        markers (loopstart, left, right, attack, …)
u32 3 (magic); u32 version | 0x1000000 (compressed; all 3190 records: 0x105 ×2667, 0x106 ×523)
u32/f32 duration_ms (u32 if version 0x105, f32 if ≥ 0x106); u32 signature; f32 param; u32 n_track
i8 rot_bits, i8 trans_bits
five delta streams, in this order and in this shape:  (bits, columns)
   idx   (32,1)  per track: bone, unused, mode, n_rot_keys, n_trans_keys   (the last is read after the rotation keys)
   time  (20 if 0x105 else 32, 1)  per key: time (float bit pattern if 0x106, integer ms if 0x105); rot keys then trans keys of a track
   rot   (rot_bits, 4)             per rot key 4 values: q = (v − 2^(rot_bits−1)), then normalised, order x y z w
   range (32, 1)                   per track: f32 bit patterns x0 x1 y0 y1 z0 z1 (translation box)
   trans (trans_bits, 3)           per trans key 3 values: p_i = (hi_i − lo_i) · v / (2^trans_bits − 1) + lo_i
delta stream = per column { u32 comp_len; u32 raw_len; zlib blob }, raw = big-endian ceil(bits/8)-byte words;
   every column is a running sum (wrapping u32) masked to `bits`; successive reads cycle through the columns, the word offset advances after the last column
```
(`FUN_1005bb82`: ctor(bits, io, columns); `FUN_1005b96a`: read.) All 3190 records decode, consuming each record up to ≤12 trailing bytes; `rot`/`trans` key counts per track are independent. The uncompressed branch (flag clear: `t, q[4]` then `t, p[3]` per key) is never used in the data and not decoded. `mode` is 2 for nearly all tracks (meaning unknown); `param` ~0 for most clips and ≈0.5 for a few (unknown). Time unit is **milliseconds** `[INFERENCE]`: keys sit at 200 ms multiples, `right`/`left` foot-step events are ~500 ms apart in walk clips and the last key coincides with `duration`.
- **Sampling** (`FUN_10051d2a/df4`): binary search for the surrounding keys; translation lerp, rotation shortest-path slerp (lerp when 1−|dot| < ε); before the first/after the last key the end key is held. The clip loops (`time mod duration`, caller's job).
- Totals: 3190 clips, 6 648 373 keys, 7520 s of animation; 168 skeleton hashes in clips vs 167 in models: 8 clips fit no model, 2 models have no clip.

### Scene assembly (`character::load_character*`)
- `load_character(store, id)` = bind pose; `load_character_posed(store, id, anim_id, time_s)` = CPU skinning of the same vertices at `time_s` (looped) with the clip's bone matrices, error if the clip's `signature` ≠ the model's. `load_character_record(store, rdb_type, id, pose)` accepts 1010027 too.
- Output follows the scene contract: Z negated, winding reversed (exactly as for static meshes), UVs untouched; one `Submesh` per material (groups merged); blend: opacity < 1 or fractional alpha ⇒ `AlphaBlend`, only 0/255 alpha ⇒ `AlphaTest`, both only if `flags & 8 == 0`; textured submeshes use white × opacity (the D3D material colours are not applied: diffuse 0.45 / ambient 0.9 would darken the skins), untextured ones the linearised diffuse. `spawn`/`spawn_look_at` frame the model from the front (characters face +Z in model space, −Z in the scene).
- **Heads**: `load_character_with_head(store, id, head_mesh_id, pose)` mounts a static `1010001` head mesh on the model's `Attractor01_head` (bone `Bip01 Head`, `pos`/`rot` in that bone's frame): `mount = W[bone] ∘ (R(rot), pos)`, applied as the instance transform (conjugated by the Z mirror). Player bodies have no skin vertices on the head bone, so in the bind pose its frame is derived: nearest fitted ancestor frame carried down the chain with the local transforms of the compatible clip whose first frame is closest to the fitted bind frames (`best_rest_clip`). Gamecode builds the head file names `head_<race><sex>%02d{,_lores,_hires}.abiff` (strings in GUI.dll); the file name → rdb id lookup is the name table (below). When a head is mounted the body's own `head` stub part is dropped.

### Name table, animation roles, player characters
- **Name table** = `rdb_1000010` id 1 (1.4 MB, `character::NameTable`): `u32 version = 7`, then sections `{ u32 rdb_type; u32 n; n × { u32 id; u32 len; char name[len] } }` for 1010001 (11828 meshes, `*.abiff`), 1010002 (805 models, `*.cir`: `athrox_male.cir` = 5900, `solitus_male.cir` = 5907, …), 1010003 (3559 clips, `*.ani`), 1010004 (13177 textures), 1010005 (empty), 1010008 (11040 icons/textures), 1010011 (60 skins). The sibling singletons 1000045/1000032 are unrelated event/data tables. char_stats: names for 767/770 models and 3168/3190 clips.
- **Clip sets / roles**: the client names clips `%s_%s_01_01.ani` (set, clip name; Gamecode.dll string). All seven player bodies share one skeleton; the set is `athrox` for Atrox, `male`/`female` for the other breeds (so opifex/nanomage use the solitus sets). Clip names present in all three sets include `idle-stand`, `idle-unarmed`, `walk`, `walk-back|left|right`, `run`, `run-back`, `sneakcool`, `idle-chair`, `idle-ground`, `idle-crawl`, `swim`, `idle-swim`, `jump-stand`, `jump-forward`, `idle-sleep-ground`, `idle-lounging`, `idle-hover`, plus attack/die/weapon clips and ~90 `social-*` emotes (`social-backflip`, `social-bow`, …); there is no `run-left/right`, `fall`, `wave`, `laugh-*`, `sleep` clip (those strings in Gamecode are other tables). `character::{model_clips, character_animations, role_anim}`; `Role` = the named roles above + `Emote(name)`, `FromStr` accepts the clip name (`walk`, `idle`, `social-bow`). Walk ids: athrox 10078, male 10191, female 10162; run 9386/10194/10146; idle-stand 9992/10173/10135. Which clip the game logic picks when (movement state machine) is code, not data: the table gives the name only.
- **Heads**: `head_<race><sex>[_asian|_african]<NN>.abiff` with race `athrox` (no sex: Atrox is male only in the data), `nano`, `opifex`, `solitus`; counts: atrox 41, nano m/f 41/43, opifex m/f 46/50, solitus m/f 57/61 (+ asian 9/7, african 9/8); `NN` is sparse (0..74). No `_lores/_hires` meshes exist in the database. Also named one-off heads (`head_solitusmale_joshua_kahn`, mutants, …). `player_heads(store, breed, gender, skin)` → `(NN, mesh id)`.
- **Skin**: the body models are textured `<part>_<race><sex>_default.png` (part ∈ body/arms/legs/hands/feet; starter armour on body/legs; hands = green placeholder). Rdb 1010011 holds the unclothed skins `<part>_<race><sex>[_<caucation|asian|african>]_naked.png` (e.g. `hands_athroxmale_naked` 9240, `body_solitusmale_caucation_naked` 8767; ethnicity only for solitus; spelling `caucation` is the client's) plus three `body_*_clad` ones. `load_player` replaces every `*_default.png` body part by its naked skin (`skin_swaps`). Default pick = naked: that is what an unequipped character shows `[INFERENCE: the client draws the defaults only for NPC/starter clothing]`.
- **API**: `Player { breed, gender, skin, head }` → `load_player(store, &player, Some((Role, secs)))`; `load_player_character(store, breed, gender, head_nn, pose)` = caucasian shortcut; `player_model(store, breed, gender)`. CLI: `aomac view player <breed> <gender> [--head NN --skin asian --role walk --time 0.6]`, `aomac view char <id> --role walk`.

### Results
`char_stats` over all records: 1010002 770/770 decoded (3 757 273 vertices, 2 948 954 triangles, 3738 texture parts, 0 failures, every record builds a bind-pose scene), 1010027 8/8, 1010003 3190/3190; posed decode of all 768 models that have a compatible clip with its first clip at mid-time: 768/768 ok. Tests: `character::tests` + `anim::tests` (hand-built records incl. zlib delta streams, skinning, blend rules), `tests/character_real.rs` (all models/clips parse, upright + 99 % normal agreement, posing/looping/skeleton check, head mounts, skips without the client).
Visual check (`aomac view char …`, screenshots inspected): 5900/5907/5927/5941/5914/5934 with their default heads (40098/40681/40630/40135/40250/40209) upright, un-mirrored, textured, heads seated on the neck; 5900 posed with `athrox_sneakcool` 9382 at 0.3–2.1 s (stride with raised leg and swinging arms, stays human-shaped; originally mislabelled walk); 5914 bind vs idle clip 9375 frame 0 identical proportions (bone scales); creatures 29902, 85335, 95326 and android 15215 posed with their first compatible clip. Round 3: `aomac view player <breed> <gender> --role idle|walk --time 0.6` for solitus/opifex/nanomage × male/female and atrox male (7 combinations; Atrox female does not exist in the client): naked skins, no green on hands/feet, heads seated, idle = relaxed stance, walk at 0.6 s = mid-stride (one leg forward, arms swinging); solitus `--skin asian --head 2` shows the asian head set with a darker skin; skin tones per race: solitus tan/brown, opifex slate-grey, nanomage grey-brown, atrox ochre-brown.
**Gaps.** `env_texture`/env maps, specular and shininess, bone attachments (`Attractor*` other than the head: weapons, shoulder pads, which `Attractor` bones apply to which items), the progressive-mesh LOD trailer and the `mode`/`param`/`alpha_aux` semantics are decoded but not used; the movement/combat state machine choosing a clip (only the names are data), clothing selection from the item records (server-side data), Atrox female (absent from the client), body-shape variants (`solitus_male_fat/thin`, robes) in the player API, the exact skin tint of the in-game lighting; uncompressed `CATAnim` keys and mesh version 0x67 are not supported (absent from the data); the bind frame of skinless bones is an approximation.

**Room lightmaps** (`dungeon::depack_lightmap`, `record.rs`). The room record stores `i32 size + 4`, `i32 vertex count`, then `size` bytes: a zlib stream (zlib 1.2.5, `FUN_1002a180`) that `n3Room_t::DepackLightmap(count, mono)` (N3 @0x10010eb7) inflates to `count * 2` bytes (`mono` = room format version > 7, which is every record; `count * 6` otherwise). `CreateDungeonRoom` (@0x10008563) applies it with `FUN_100082a7`: u16 *i* becomes the diffuse colour of **final shell vertex *i*** (welded, in emission order) `R = (v & 0x1f) << 3`, `G = (v >> 5 & 0x3f) << 2`, `B = (v >> 8) & 0xf8`, alpha 255 (a stream shorter than `count*2` paints every vertex white). `VisualRoom_t::Init` (DisplaySystem @0x1006e133) sets `D3DRS_DIFFUSEMATERIALSOURCE/SPECULAR/AMBIENT = material` and `EMISSIVEMATERIALSOURCE = COLOR1`, material ambient 0.8, diffuse white: **the baked colour is emissive light**, `lit = tex * (lightmap + 0.8 * ambient + dynamic lights)`. We emit `Submesh.prelit` (renderer: `tex * material * (vertex.rgb + 0.8 * ambient)`, no sun / point lights). Values are dark (mean ≈ (36, 48, 44)/255, 38 % zero) because they are *added* to the ambient term.
To make the vertex order match the client, the weld was ported exactly: the candidates of `FUN_10001645` are the vertices of the cells (x−1..x+1, z−1) (ring `A[0]..A[3]` of per-cell vertex counts in `CreateDungeonRoom`) and of the previous cell up to the current block (`A[w]`), compared by position / normal / uv only (**not** per material), in index order; the piece order inside a cell is corner posts, floor piece, main piece (`FUN_10001c3b` list build). Result over all 2000 rooms of the 601 playfields: vertex count == lightmap count for 97 % (127, 346, 386, 331: 183/189); rooms that still differ (a few vertices; larger gaps are the known missing door frames) keep the plain ambient look. Indoor ambient = record ambient bytes (max with 0.01) instead of the old 0.45 fill, no sun.
*Material slot 0*: most tilemaps list material id 1 first (unpainted cells use layer value 0 → rdb 1010009/1, the "Error" placeholder image of the PRK database). `VisualRoom_t::AddMaterial` (@0x1006e916) pairs every material with the fallback texture `darkrock_tileable.png`, so material 1 is drawn with that texture.
